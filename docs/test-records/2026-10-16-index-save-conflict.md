# 目录过期保存保护

日期：2026-10-16。

## 问题与复现

两台设备读取同一目录后，A 修改标题并保存；B 未刷新页面便修改说明、提交完整字段。原有草稿冲突提示只比较页面快照，不读取实际最新内容；后端不校验基准，因此 B 会把 A 的标题改回旧值。

新增 `apps/api/tests/indexes.test.mjs` 复现先失败：`Missing expected rejection`，原 12 项通过、新增 1 项失败。使用内存上游替身执行真实保存函数，不访问真实账号或修改远端目录。随后补路由集成测试，断言只有 A 写入、B 返回 412、最终目录保留 A 的修改。

## 最小修复

- 新客户端保存时携带 `expected: { title, desc, isPrivate }`，来自草稿的原始基准，不把当前输入或 trim 后的值当作基准。
- API 校验基准结构，使用当前授权重新读取目录并校验上游字段。逐字段不一致返回 `412 index_edit_conflict`；读取失败或响应损坏不继续 PATCH。读取绕过缓存并设置 12 秒超时。
- 使用 412 避开已有 409 授权失效约定。客户端显示关闭编辑器并刷新后重新确认的提示，保留草稿与原始基准。
- 更新路由接受手机客户端已有的 `isPrivate` 字段，仍兼容旧的 `private` 名称，确保可见范围参与比较及保存。
- 服务端允许省略 `expected`，兼容已发布客户端；新客户端的类型要求提供基准。新客户端与新 API 必须一起生效。

## 边界

这不是原子 compare-and-swap。两个请求若都在对方写入前完成读取，仍可能同时通过检查并覆盖；上游网页及其他客户端也不受约束。旧客户端没有编辑基准的写入仍沿用原行为。没有增加进程内锁来假装解决跨 Worker／跨设备并发。
