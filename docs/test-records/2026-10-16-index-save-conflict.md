# 目录过期保存保护

日期：2026-10-16。

## 问题与复现

两台设备读取同一目录后，A 修改标题并保存；B 未刷新页面便修改说明、提交完整字段。原有草稿冲突提示只比较页面快照，不读取实际最新内容；后端不校验基准，因此 B 会把 A 的标题改回旧值。

新增 `apps/api/tests/indexes.test.mjs` 复现先失败：`Missing expected rejection`，原 12 项通过、新增 1 项失败。使用内存上游替身执行真实保存函数，不访问真实账号或修改远端目录。随后补路由集成测试，断言只有 A 写入、B 返回 412、最终目录保留 A 的修改。

## 最小修复

- 新客户端保存时携带 `expected: { title, desc, isPrivate }`，来自草稿的原始基准，不把当前输入或 trim 后的值当作基准。
- API 校验基准结构，使用当前授权重新读取目录并校验上游字段。逐字段不一致返回 `412 index_edit_conflict`；读取失败或响应损坏不继续 PATCH。读取绕过缓存并设置 12 秒超时。
- 使用 412 避开已有 409 授权失效约定。客户端显示关闭编辑器并刷新后重新确认的提示，保留草稿与原始基准。
- 更新路由接受手机客户端已有的 `isPrivate` 字段，仍兼容旧的 `private` 名称，确保可见范围参与比较及保存。
- 服务端允许省略 `expected`，兼容已发布客户端；新客户端的类型要求提供基准。新客户端与新 API 必须一起生效。

## 边界

这不是原子 compare-and-swap。两个请求若都在对方写入前完成读取，仍可能同时通过检查并覆盖；上游网页及其他客户端也不受约束。旧客户端没有编辑基准的写入仍沿用原行为。没有增加进程内锁来假装解决跨 Worker／跨设备并发。

## 后续切片：重叠请求的原子占用

用户要求继续关闭读取与写入之间的窗口，并打开 iOS 模拟器验证。

### RED → GREEN

新增基于真实 Miniflare D1 的路由测试：两个独立 `createApp` 实例共用数据库和上游替身；A 已读完快照、正在 PATCH，但暂不完成，B 此时保存。原代码 B 返回 200，断言预期 423 失败，确认两个请求均已进入读写链路。加入保护后，B 在读取前即返回 423，只有 A 发出一次 PATCH，最终内容保留 A 的修改。没有用 sleep 构造时序，用 Promise 闸门精确控制。

D1 新表以账号＋目录作为主键，单条 `INSERT … ON CONFLICT DO NOTHING` 原子争用，通过 `meta.changes` 判断取得占用；释放包含操作 UUID 条件。依据 [D1 SQL 支持](https://developers.cloudflare.com/d1/sql-api/sql-statements/) 和 [D1 返回值约定](https://developers.cloudflare.com/d1/worker-api/return-object/)。检查和 PATCH 全在保护范围，DELETE 也复用；没有新增外部服务、依赖或进程内锁。

上游写入 200／204 或明确 4xx 拒绝后释放；超时、网络中断、5xx、202 等未知结果保留占用并返回 423。没有自动过期。新 Worker、很旧的 created_at 均不能绕过，后续操作不再触达上游。预读失败和基准冲突在未写入时释放。具体恢复与部署顺序见部署指南。

### 剩余边界

保护范围是经过同一 D1 的同账号同目录 Kaku PATCH／DELETE。上游网页或其他客户端仍可并发写入；旧客户端不含编辑基准时仍存在顺序覆盖。进程异常可能留下待人工核查记录，这是避免未知写入被下一次操作超越的明确取舍。没有部署迁移、部署 API、推送或发版。
