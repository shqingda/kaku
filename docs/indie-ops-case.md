## 1. 产品是什么

Kaku 是面向 iOS / Android 的**第三方 Bangumi 客户端**。一个人维护，仓库同时是产品和学习项目。

三件套：

| 应用 | 路径 | 实际职责 | 运行在哪 |
| --- | --- | --- | --- |
| 移动端 | `apps/mobile` | 用户天天打开的东西 | 用户手机（Expo SDK 57 / RN 0.86） |
| API | `apps/api` | OAuth、会话、登录后写操作代理、偏好/推送/公开缓存 | Cloudflare Workers + D1 + KV |
| 官网 | `apps/web` | 介绍、隐私政策、服务条款、FAQ | Cloudflare Workers 静态资源 |

产品原则（见 `AGENTS.md`）：

- Bangumi 是 adapter，不是领域模型。
- 失败必须显式：离线、重试、挂了，不能变成空白 loading。
- 一次只做一小片垂直功能。
- 能在面试里讲清楚的代码，优于巧妙抽象。
- 免费额度当现金管。

安全边界：密码只在 Bangumi 官方页输入；`client_secret` 和 OAuth token 只在服务端；App 回调只带一次性 handoff code。

发布状态（2026-08-27）：

- 功能面已经接近「能当日常客户端用」：浏览、收藏、进度、社区、深色模式、偏好云同步、离线条目包、主屏幕快捷方式、AniList 增强、Expo 推送骨架。
- **还没上架**。缺 Apple / Google 商店凭据、商店截图与描述。Android 日常包走本地 split APK + GitHub Releases（debug 签名，升级须先卸载）。
- EAS 免费云构建额度 2026-08 已用尽，约 9/1 重置。正式 Play AAB 等额度恢复。
- 上游卡住的能力（小组加入/退出、删除动态、角色人物取消收藏）故意不做。
- 明确不做：i18n（Bangumi 没有外语用户盘）、在上游稳定前做 JS Widget。

## 2. 用户到底是谁（比功能更先想）

Bangumi 本体是中文 ACG 条目/收藏/讨论社区。2026-05-26 前后 `bgm.tv` 被墙。之后还在用的人，几乎都满足下面之一：

1. **国内、已经开代理的用户**（主流）：小米 / OPPO / vivo 及少量华为 Android，加上 iOS。他们本来就会翻墙看番、上 Bangumi。
2. **真海外用户**（少部分）：留学、移民、港澳台日韩，设备带 GMS 或纯 iPhone。
3. **完全没代理的大陆用户**：打不开 `bgm.tv`，也常常打不开 Cloudflare Workers。Kaku 当前架构帮不了他们，除非以后换国内可达的入口。不要把他们算进可服务市场。

推论：

- Kaku 的目标用户 ≈「本来就会用 Bangumi 的人」里，愿意装第三方客户端的那一小截。
- 不是「全中国安卓用户」，也不是「全球二次元」。
- 因此：商店语言以中文为主、不值得做 i18n、推送渠道必须按国产安卓 + iOS 来想，而不是按「Firebase 教程默认的海外安卓」来想。

## 3. 基础设施现实：你其实有四层会挂

用户感知的「Kaku 挂了」可能是下面任意一层，且经常叠在一起。

```
用户设备
  ├─ 本机系统 / App 进程 / JS bundle / 本地缓存
  ├─ 用户网络（无网、公司网、代理规则漏了某域名）
  ├─ Kaku API（*.workers.dev，Cloudflare）
  │     └─ 再转 Bangumi（api.bgm.tv / next.bgm.tv / bgm.tv）
  └─ 第三方旁证（status.bgm.tv → bgm-status.ry.mk，也在 Cloudflare）
```

关键耦合：

- 登录、写收藏、推送登记都走 Workers。Workers 挂了或被墙，**已登录能力全没**。
- 公开浏览：App 也可直连 Bangumi adapter；无网时靠 TanStack Query 持久化（公开查询 24h）和最近 10 条条目的 30 天离线包。
- `kaku-api.shqingda.workers.dev` 和 `status.bgm.tv` 都在 Cloudflare 上。大陆无代理时，**「检测 Bangumi 是否挂了」的网站自己也可能打不开**。
- Bangumi 有分流：`bgm.tv` 网页挂了，`api.bgm.tv` 可能还活着。Kaku 用的是 API / P1，不是官网 HTML 首页。

已有、且不依赖服务端的本地能力：

- `expo-network`：明确「互联网不可达」才标离线，驱动 React Query 重连刷新。
- 顶栏 `OfflineBanner`：「当前离线，显示的是缓存内容」。
- `/diagnostics`：本机错误记录，可分享，不含凭证。
- 公开查询持久化 + 条目离线包。

首页缓存彻底失效、用户进不去 App 的内容区：这种情况文档约定为不可解，诊断功能也可以一起放弃。

## 4. 决策一：要不要把 status.bgm.tv 接到 App 里

### 它是什么

[status.bgm.tv](https://status.bgm.tv) 不是 Bangumi 官方监控。它是第三方项目 [maho0x/bangumi-status](https://github.com/maho0x/bangumi-status)（MIT），`status.bgm.tv` 302 到 `https://bgm-status.ry.mk/`。

公开 JSON：

```http
GET https://bgm-status.ry.mk/api/status
```

响应要点（2026-08-27 实测，整体 `status: ok`）：

- 8 个组件：`bgm.tv` / `bangumi.tv` / `next.bgm.tv/p1` / `api.bgm.tv`，各分 Guest 与 Authenticated。
- 另有 `/api/probes`、`/api/feed.atom`、`/api/online`、`/api/wiki-stats`。
- 探针约 15 个：含 cn、hk、jp、sg、kr、us、gb、lt。延迟 >5s 标 Degraded，多数仲裁防误报。
- HTTP 缓存约 20 秒。维护者说明曾极度缺大陆探针，现已有 cn 节点，但仍是「全球视角」，不是「这个用户的手机视角」。

### 能不能当用户的唯一检测

不能。原因：

1. 站点本身在 Cloudflare。用户打不开 Kaku Workers 时，常常也打不开 status。
2. 全球探针显示 Operational，不代表这台小米手机能连 `api.bgm.tv`。被墙、代理分流、DNS 污染都会造成「他挂我好」或「他好我挂」。
3. Guest 与 Auth、网页与 API 会分别炸。只显示一颗总绿灯会误导。
4. 第三方服务以后可能改 schema、换域名、关掉。App 不能把它当硬依赖。

### 推荐（尚未实现，需另开开发会话）

**可以接入，但只能当旁证。主检测必须是本机并行探测 + 上次成功结果落盘。**

建议做成「账户 → 诊断信息」里的一节「服务状态」，不进首页，避免吓到只是缓存慢的用户。

本机并行、短超时（约 3–5s），互不依赖：

| 探针 | 打谁 | 成功意味着 |
| --- | --- | --- |
| 本机网络 | `expo-network` | 设备认为有互联网 |
| Bangumi API | `https://api.bgm.tv/v0/` 某个极轻公开端点 | 这台设备此刻能直连 Bangumi |
| Kaku API | `https://kaku-api.shqingda.workers.dev/config` | 这台设备此刻能连 Workers |
| 全球旁证 | `https://bgm-status.ry.mk/api/status`（可选再 mirror `status.bgm.tv`） | 海外探针觉得 Bangumi 活着 |

把每次成功快照写入本机（sqlite/kv），带时间戳。无网或三次都失败时，展示「上次检测 · 相对时间」，并写明这是缓存。

判定表（给用户看人话，不看 HTTP 码）：

| 本机网 | Bangumi | Kaku | status.bgm.tv | 对用户说 |
| --- | --- | --- | --- | --- |
| 无 | — | — | — | 本机没网。下面是上次结果。 |
| 有 | 失败 | 失败 | 失败 | 出境或 Cloudflare 方向不通，更像代理/墙，不是 App 自己崩了。 |
| 有 | 失败 | 成功 | 全球正常 | Bangumi 在你这边连不上，但 Kaku 服务和全球侧正常。 |
| 有 | 失败 | 成功 | 全球挂 | Bangumi 大概率真挂了。 |
| 有 | 成功 | 失败 | 任意 | Kaku 服务连不上（Workers 挂了或被墙）。公开浏览若直连 Bangumi 仍可能可用；登录/同步不可用。 |
| 有 | 成功 | 成功 | 失败 | 检测站自己挂了，忽略它。 |
| 有 | 成功 | 成功 | 成功 | 链路正常。若界面仍不对，看本机诊断日志（更像 App 问题）。 |

「App 挂了」不要用网络探针证明：用现有本机错误记录 / Sentry。进程都起不来时任何功能都无效。

离线可用性边界：

- 诊断页是本地路由，不该依赖 Workers 才能渲染。
- 无网时只读本地快照。
- 唯一放弃条件：用户清了本地数据，或公开缓存 24h 过期且内容区已经进不去——与现有离线策略一致。

不要做：把 status 页面 WebView 塞进 App；不要为了检测再加一个会挂的自建监控机（独立开发者养不起第二套观测）。

## 5. 决策二：被墙后流量大概剩多少

没有官方 DAU API。公开能核对的，是 bangumi-status 从 `https://chii.in/wiki/stats` 抓的每日站务数字（2026-04-28 至 2026-08-26）。墙的时间按社区记录约 **2026-05-26**。

用「墙前 28 天（04-28–05-25）」对「墙后 92 天（05-27–08-26，去掉 08-27 当天未满日）」：

| 指标 | 墙前日均 | 墙后日均 | 剩余 |
| --- | --- | --- | --- |
| 新注册 | 350 | 271 | **约 78%** |
| 收藏动作 | 31,000 | 38,000 | **约 123%**（不降反升） |
| 新话题 | 131 | 119 | **约 91%** |
| 回复 | 3,025 | 2,615 | **约 87%** |

墙后最近 14 天 vs 墙前最后 14 天：注册约 **69%**，话题/回复约 **83%**。周线看，注册从墙前约 380–420/天下到 180–280，回复从约 2800–3500 下到 2300–2700 后稳住。在线人数旁证（status 近 24h）大约 3 万级，峰值曾到约 8 万，说明登录用户盘还在。

必须拆开说的两件事：

1. **裸连 `bgm.tv` 的大陆访问量**  
   被墙后应接近归零。这类流量大概只剩海外出口、漏网和已经开代理但统计记在境外 IP 的人。若问的是「搜索引擎/第三方流量盘里的 bgm.tv」，剩 **10–25%** 这种数不奇怪，而且地理分布会严重失真。

2. **还能登录做事的人（Kaku 真正的市场）**  
   Wiki 日活说明：硬核用户大多已经有代理或改走 `chii.in` 等域名。社区动作大约还在墙前的 **70–90%**。收藏上升很可能是「留下的人更勤」加上夏季番，不能理解成网站变大了。

对 Kaku 的估算（面试里要带误差带）：

- 可服务用户盘相对墙前 Bangumi 活跃用户：**大约 70–85%**。
- 其中会装第三方客户端的比例本来就小，墙本身不是主过滤器；**代理摩擦、发现渠道、信任**才是。
- 新用户获取伤得比老用户留存重（注册下滑更明显）。Kaku 获客不要幻想「墙把官方 App 掐死所以人人转投你」——官方站活着，只是要梯子。
- 不要用 Semrush 一类全球面板做国内产品决策。

## 6. 决策三：推送怎么做（先渠道，后 SDK）

先不谈收费。问题是：通知怎么到达你真正的用户手机。

### 分层

| 人群 | 设备现实 | 能用的通道 | 现在仓库里的状态 |
| --- | --- | --- | --- |
| 国内 iOS | APNs 在国内大体可用 | **APNs**（经 Expo Push） | 已接骨架；需真机 native 包 |
| 真海外 Android / 国内带 GMS 的机器 | Play 服务活着 | **FCM**（经 Expo Push） | 代码有，缺 `google-services.json`，真机登记失败 |
| 国内主流 Android（米 OV、部分华为） | 无 GMS，厂商通道 | **厂商推送或国内聚合** | 未做。FCM 对此人群基本等于没有 |
| 所有人打开 App 时 | 不依赖推送通道 | **拉取未读** | 已有通知页；Cron 15 分钟只服务于已登记 token |

Expo Push 不是第四种全球协议，它只是 **FCM + APNs 的代发件箱**。国内用户「开了代理」**不能**让 FCM 在小米/OPPO 上复活：缺的是 Play 服务和厂商允许的常驻长连接，不是 HTTP 出站。

### FCM 在这个产品里怎么用

保留，当作「海外 Android + 少量带 GMS 的国内机」方案：

1. Firebase 项目 → `google-services.json` 打进 Android 包（debug 与 release 各一份或同一套）。
2. Expo Notifications 继续拿 Expo Push Token，服务端仍 `POST https://exp.host/--/api/v2/push/send`。
3. 在设置页把失败原因说成人话（已做：缺 google-services 时不再只说「请稍后重试」）。
4. 不要对米 OV 用户承诺「打开开关就能收到」。开关失败要指向真实原因。

FCM 对独立开发者：**免费额度对 Kaku 这种体量足够**，贵的是 Google 账号、隐私文案和「它打不到目标机」。

### 除了 FCM，国外还有什么

能真正把系统通知弹到手机上的全球方案，本质上仍是两条：

- **APNs**：iPhone / iPad。这是国内 iOS 用户的正确通道，优先保证它。
- **FCM**：带 GMS 的 Android。

其余几乎都是包装：

- OneSignal、Airship、Pusher Beams、Amazon SNS、Azure Notification Hubs、Expo Push：底下还是 APNs/FCM。
- Web Push：对已上架的原生 App 无意义。
- UnifiedPush / ntfy / Gotify：极客自托管，不能当主流用户方案。
- Huawei HMS Push 海外：只覆盖华为海外机。

**没有一种「国外方案」能覆盖国内小米/OPPO/vivo/华为。** 那是国内厂商通道的地盘。

国内若以后要做（另开开发，先评估隐私合规与 SDK 体积）：

- 聚合：个推、极光、友盟、腾讯云 TPNS、阿里云移动推送。一个聚合换多家厂商，代价是隐私政策、可能的备案/账号、包体积。
- 或自接华为/小米/OPPO/vivo/荣耀，每个都要开发者账号与应用审核。

独立开发者现阶段建议：

1. **iOS 用 APNs，把它做对。** 这覆盖目标用户里体验最好、付费意愿相对高的一截。
2. **FCM 作为海外 Android 方案保留**，配好 google-services 即可，不要再叠 OneSignal。
3. **国内 Android 第一年不要承诺推送。** 打开 App 拉未读 + 可选本地提醒（若系统允许）是诚实 MVP。等有真实 DAU 再买聚合的账。
4. Cron 15 分钟轮询已经依赖 Workers 和用户仍登录。Workers 被墙时，推送登记和投递都会失败——又回到「目标用户必须能出网」。

## 7. 当前运营体检（一个人的真实约束）

已经做对的：

- 范围克制：上游没有的接口不猜。
- 显式失败与离线包，符合「不能空白 loading」。
- 免费档 Cloudflare（D1/KV/Cron/Cache API）先用完再谈付费。Queue 评估后暂缓。
- 发版分两条：日常本地 split APK 不烧 EAS；上架才走云端。
- 崩溃有 Sentry；敏感信息不进诊断分享。
- 官网有隐私政策和条款，商店审核会用到。

正在疼的：

- 目标用户在墙内，后端在 Cloudflare，数据源也在墙外。三层同命运。
- 推送骨架按海外教程接了 FCM，和主流设备错位。
- 没上架：发现渠道只剩 GitHub / 口碑 / Bangumi 小组。debug 签名导致用户升级摩擦。
- 本地 APK 不传 source map，崩溃能报不能精确定位。
- 代理环境会让 `git push` / EAS 上传假死（必须 unset `http_proxy` 等）。这是运营流程的一部分，不是偶发。
- 一个人同时是产品、客户端、Workers、发版、客服。

明确不要做的（到有新证据再翻案）：

- i18n。
- 为没代理的大陆用户做国内中转（那是另一款产品：合规、成本和「你在镜像 Bangumi」的风险都变了）。
- 在没 DAU 前接 4 家厂商推送 SDK。
- 把 status.bgm.tv 当唯一健康信号。

## 8. 课程大纲（教学任务按此顺序）

每课：概念 → Kaku 实例 → 一道学生必须回答的题。不要一次倒完。

1. **先写清用户，再选技术。**  
   为何「国内 Bangumi + 代理 + 米 OV / iOS」决定了 i18n、推送、Workers 的命运。

2. **你卖的是自己的客户端，库存却在别人仓库。**  
   adapter 与领域模型；上游 500 时如何停功能而不是猜接口。

3. **画故障地图，而不是只画功能架构图。**  
   四层会挂；为何「用户说 App 挂了」要先问哪一层。

4. **免费额度是现金。**  
   EAS、Workers、D1、KV、Sentry、Expo Push。哪笔钱还没到该花的时候。

5. **推送是渠道问题。**  
   APNs / FCM / 厂商 / 打开 App 再拉。为何加 OneSignal 解决不了小米。

6. **离线与诚实。**  
   缓存 TTL、离线包、横幅文案、诊断页。何时该说「我也不知道」。

7. **发版是产品。**  
   debug 签名、卸载升级、ABI 拆包、商店凭据、隐私政策 URL、release notes 用英文的原因。

8. **发现与信任。**  
   没上架时人从哪来；第三方客户端如何让人安心把 Bangumi 账号授权给你。

9. **什么时候开始想钱。**  
   先不收费。收费前必须先有可服务用户、稳定通道、和明确加值（Kaku 自有功能 vs 镜像官网）。

10. **一个人的工作系统。**  
    一次一小片、文档当备忘、代理与 CI 踩坑清单、把「运营课」和「写代码」拆成不同会话。
