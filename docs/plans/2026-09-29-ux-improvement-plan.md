## 目标与取舍

让用户少丢内容、少误操作、少猜状态，并记住重复使用时的习惯。

推荐顺序：先保护历史和输入，再补清楚的反馈，最后增加便利功能。每个编号独立完成实现、验证与提交，上一项收口后再开始下一项；不把整个阶段合成一次大改。

已有的回复草稿、收藏筛选记忆、单集评论位置恢复、分页重试、危险收藏变更确认继续复用。保持现有导航结构；首页卡片不增加快捷记进度。暂不引入离线写队列、跨设备进度合并或新的 UI 框架。

## 第一阶段：保护用户数据和输入

### A1. 拆分缓存清理与历史删除（首个切片）

**问题：** 当前“清理本地数据”把缓存、离线包、搜索历史、浏览历史和诊断记录一起删除；历史清除还可能同步到其他设备。即使确认框有说明，用户腾空间时仍容易删除想保留的记录。

**推荐方案：** 提供“清理缓存”和“管理历史记录”两个入口。前者清理可重新获取的内容及图片缓存，说明会移除自动离线内容；保留历史、草稿、偏好和登录。后者分别清除搜索或浏览历史，执行前说明当前同步设置下影响哪些设备。诊断记录沿用诊断页自己的清理入口。

**实施入口：** [账户设置菜单](../../apps/mobile/src/features/account/account-settings-menu.tsx)、历史 Provider、查询持久化模块。先核对实际缓存范围，尤其是私有查询缓存，避免菜单文案与清理行为不一致。

**验收：**

- 清理缓存后仍可登录使用，草稿和历史保留，不触发云端历史删除；重新打开内容可以恢复缓存。
- 清理过程中防重复操作，部分失败有明确结果和重试入口；检查返回失败值和抛异常两种情况。
- 清除搜索历史不影响浏览历史；取消确认不产生删除；同步开启、关闭及账号切换的作用范围与文案一致。

### A2. 为新建话题补持久化草稿

**问题：** 回复已能恢复本机草稿，但新建话题的标题和正文仍放在组件内存中；进程结束会丢失长文本。

**推荐方案：** 先覆盖条目话题和小组话题。按账号、目标类型和目标标识保存标题与正文，复用回复草稿的行为约定。关闭后可恢复；只有明确丢弃或确认发送成功才清理。显示真实的保存状态。

**实施入口：** [话题编辑器](../../apps/mobile/src/features/discussions/topic-composer.tsx)、[回复草稿 Hook](../../apps/mobile/src/features/discussions/use-reply-draft.ts)。优先用可解释的小模块，不预先设计万能表单框架。

**验收：**

- 关闭重开、页面重挂载、杀进程重启后，标题与正文都能恢复。
- 不同账号、不同话题目标互不覆盖；旧请求迟到成功不会清除后来编辑的草稿或关闭新编辑器。
- 保存失败时内容仍在，并可重试；发送失败保留草稿；发送成功但清理失败时只提示重试清理，避免重复发送。
- 显式丢弃需要确认；存储读取失败不得用空内容覆盖已有草稿。

### A3. 将草稿保护扩展到其他编辑器

在 A2 行为稳定后，先发布动态，再新建目录、编辑目录，各自作为独立切片。

目录需保存标题、说明和可见范围；编辑草稿按账号与目录 ID 隔离。重新打开时若服务端内容已变化，提示选择恢复本机草稿或使用最新内容，避免静默覆盖。复用 A2 的恢复、失败、账号隔离与迟到响应验收；目录原内容与草稿相同不算未保存修改。

## 第二阶段：把状态和恢复路径讲清楚

A3 可以后排，建议首轮先完成 A1、A2 与 B1–B3。

| 切片 | 用户问题与推荐改动 | 验收标准 |
| --- | --- | --- |
| B1 搜索反馈 | 结果数为零仍显示“查询中”。用请求状态区分加载、空结果、失败和已有结果刷新 | 搜索完成为零时显示“0 个结果”；失败不继续显示查询中；条目、角色、人物搜索文案与类型一致；刷新失败保留已有结果并可重试 |
| B2 通知权限恢复 | 权限被拒绝后只有说明。增加“打开系统设置”，返回应用时重查权限 | 权限未开、正在登记、登记失败分别有明确反馈；返回后开关与实际状态一致；打开设置失败可重试；检查权限不重复弹授权框，重新登记遵守当前账号和本机推送意愿 |
| B3 同步反馈 | 状态主要依赖图标颜色，失败项的重试操作不明显。显示“正在同步／已同步／同步失败 · 重试”等文字 | 未登录、关闭同步、服务不可用不显示已同步；三类同步状态各自准确；重试中有反馈；大字体可读、操作可触达、读屏标签不重复 |

实施入口：[搜索结果](../../apps/mobile/src/features/discover/explore-search-results.tsx)、[设置](../../apps/mobile/src/app/settings.tsx)、推送 Hook 与偏好/历史 Provider。

“上次同步时间”不列入 B3 首版：本地编辑时间不能冒充同步成功时间。需要增加可靠的成功记录后再展示。

## 第三阶段：记住习惯，补齐细节

| 切片 | 推荐范围 | 验收标准 |
| --- | --- | --- |
| C1 记住浏览偏好 | 首页上次选中的媒体类型、章节格子/列表布局先保存在本机；音乐仍默认曲目列表。两处可分开交付 | 重开及重启后恢复；首次使用和无效旧值有合理默认值；恢复时不闪回默认选项；清理缓存保留偏好，不扩展云同步协议 |
| C2 章节状态可理解 | 为已看、已放送未看、未放送/时间未知补文字或符号提示；统一格子与列表的无障碍状态描述 | 不靠颜色也能区分状态；日期未知不标为已放送；读屏能知道集数、状态与点击结果；浅深色和大字体下不挤压 |
| C3 表单键盘衔接 | 目录标题框的“下一项”真正聚焦说明框；顺查话题标题到正文的相同路径 | iOS/Android 键盘动作与按钮文案一致；多行正文换行不触发提交；键盘不遮挡当前编辑位置 |
| C4 排版与触控复核 | 先检查此次涉及的账户、设置、编辑器和章节页，再逐页检查核心阅读页 | 重要信息不被单行裁切；大字号下按钮仍能操作；小操作补足触控区域；迁移所改页面剩余裸字号和间距到 `TYPE`/`SPACING` |

实施入口：[首页](../../apps/mobile/src/app/index.tsx)、[章节区](../../apps/mobile/src/features/subject-detail/episode-section.tsx)、[目录编辑器](../../apps/mobile/src/features/indexes/index-composer.tsx)、[设计常量](../../apps/mobile/src/constants/design.ts)。

C4 同时是每个切片的完成要求，不等到最后统一大改。保留必要的文字缩放限制前，先验证内容能否通过换行与自适应容器完整呈现。

## 验证与交付

每个切片遵循同一流程：确认当前行为 → 实现一个完整用户路径 → 相关验证 → 审查完整 diff → 本地提交并更新记录。推送仍需明确请求。

- **逻辑和组件：** 草稿、清理与同步增加有意义的状态转换、失败和账号竞态测试；小文案或样式修改以受影响页面验证为主，不写只复述实现的测试。运行相关类型检查；共享逻辑变化按影响范围扩展回归，命令见 [测试指南](../development/testing.md)。
- **模拟器：** 走查入口、成功、失败、取消和重开路径；涉及布局时检查浅深色、大字号、键盘，涉及动效时检查可中断及减弱动态效果。可用现有 Maestro 流程验证的优先复用。
- **真机：** 杀进程后的草稿恢复、系统权限往返、实际 VoiceOver 朗读、系统断网与双设备同步分别记录。Android 实机继续遵守现有暂缓约定，未执行的项目明确列待验收。
- **真实写入：** 发布话题、动态等线上闭环使用专用测试账号和测试讨论；不能用组件替身结果宣称真实发送通过，也不向公开讨论随意发测试内容。
- **记录：** 实现完成和设备验收完成分开标注，证据放入 `docs/test-records/`；剩余验收同步到 `TODO.md`。当前草案不预填完成状态或承诺发版日期。

所有修改遵守 [协作规则](../../AGENTS.md)：保持领域与 Provider 分离；新动效从当前屏幕值开始、继承速度并可中断；工作线程回调遵守 worklet 限制；失败、离线和重试必须可见。
